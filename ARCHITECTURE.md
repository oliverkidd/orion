# How Orion works

Orion is a tmux-style terminal multiplexer for AI coding agents. You run multiple Claude / Codex / Cursor / Grok / OpenCode CLI sessions across git repos and worktrees, and they keep running after you close the UI.

## Process model

There are two processes, same binary:

1. **Daemon** (`orion daemon`) — owns every PTY, SQLite, git worktrees, and agent status. Lives in the background.
2. **TUI** (`orion`) — a ratatui client. Quit it and nothing dies; relaunch and scrollback is replayed.

On launch the TUI connects to a unix socket (`daemon.sock` in `$XDG_RUNTIME_DIR/orion/`, else `/tmp/orion-<uid>/`, mode `0700`). If nothing is listening, it spawns `orion daemon` in its own session (`setsid`) so the daemon outlives the client, does not get Ctrl+C, and holds no controlling terminal — daemon subprocesses that run the user's interactive shell must not be able to reach the TUI's tty via `/dev/tty`.

IPC is length-prefixed MessagePack: the client sends `ClientRequest`s (CRUD, attach, keystrokes, resize); the daemon pushes `ServerEvent`s (entity deltas, status, PTY output).

## Domain tree

Everything is nested:

**Project** (a git repo) → **Worktree** (main checkout or `git worktree add`) → **Session** (an agent *or* a plain terminal tab).

Every project is in one list — there is no grouping above it. One repo is one project: adding a path that resolves to a repo already registered (its root or any checkout of it) is refused. The TUI shows one project's sessions at a time and moves between projects with its PROJECT TABS; every other project's sessions keep running (and keep receiving status updates) in the background.

Worktrees are real git worktrees, created under `<repo>/../.orion-worktrees/<repo-name>/<branch>`: one hidden folder beside the repos, one subfolder per repo. Checkouts orion cut into the old `<repo>/../<repo-name>-worktrees/` folder move there at daemon boot, before any session respawns (`orion-daemon/src/relocate.rs`): compose stacks running only from a checkout are stopped first, and a checkout another process is still using stays put until a later boot. The daemon also polls git metadata so worktrees created outside Orion still show up.

An agent is a PTY running `claude`, `codex`, `cursor-agent`, `grok`, or `opencode` in that worktree. Restart resumes the stored session id when there is one, the way each CLI takes it (`--resume <id>` for Claude, Cursor and Grok; `codex resume <id>`, `opencode --session <id>`). A daemon restart (an upgrade, `orion kill`, **Restart orion**) takes every PTY; the new daemon's boot sweep marks the rows that were mid-turn (`running` / `needs_feedback`) `disconnected` and `Daemon::resume_interrupted` boots them again on their session id, staggered like the prewarm sweep — opening on a "carry on" prompt for the CLIs that take one on a resume (the relocation notice's `relocation_prompt` flag), so the turn picks up with nobody attached. The hook drain stops when shutdown begins, so the hooks the dying CLIs fire cannot overwrite that mid-turn record. Idle rows still resume on their next attach.

Persistence is SQLite at `~/Library/Application Support/dev.orion.orion/orion.db`: projects, worktrees, agents (kind + CLI session id, plus a PR URL when the AGENT was created from one), links, last UI selection.

A worktree can carry a stored **link list**: URLs pinned to a checkout, normalized to http(s). No request creates one and the grid draws none; the daemon keeps the stored rows and answers `UpdateLink` / `DeleteLink`. What a band does show is what nothing stores: the pull request on that branch, looked up client-side with `gh pr view` on the git-poll tick and cached per worktree.

The PULL REQUESTS MODAL has a separate creation path: `Enter` on a pull request in its list starts a local SESSION for it (its `Tab` / `Shift+Tab` hand the keys between the list and the PULL REQUEST PAGE beside it). The TUI sends `CreatePrAgent` with the PR URL and the branch the PR's checkout is on — its head branch, or `<owner>/<head>` for a fork's (`pull_request::checkout_branch`), since a fork's `main` must match neither the ROOT WORKTREE nor `origin/main`; the daemon finds the project's worktree on that branch, or cuts one (from `origin`'s branch of that name, else from `refs/pull/N/head`, which it then makes the branch's upstream), and the AGENT starts there — and that checkout's band wears the pull request on its rule. The daemon validates and stores it, and composes the URL plus the PR-only work rule into Claude's existing `--append-system-prompt`. Every later cold spawn or RESUME rebuilds the same system prompt from SQLite. `Enter` in the modal opens the QUICK PROMPT for the PR, whose own `⌘U` (`^X`) picks an AGENT PRESET; it sends the same `CreatePrAgent` with the typed task — wrapped in the preset's text, the task at its `{task}`, when one is on — as its `starting_prompt`, so the first prompt and the PR rule arrive together; the daemon finds the project's worktree on the PR's head branch, or cuts one, either way.

The modal also opens, merges, edits and closes pull requests, client-side and through `gh` alone (`orion-tui/src/pr_actions.rs`, each a form in the reading pane's place): `⌘N` reads the project's branches and the commits between the two picked (to fill the title and description the way `gh pr create --fill` does), then pushes the head branch to `origin` — setting its upstream when it has none — and runs `gh pr create --head --base --body-file -`; its **Promote** mode (`pr_actions/promote.rs`) opens the base into the repo's default branch from origin's branches, pushing nothing, its description built from the pull requests whose merge commits are in `origin/<default>..origin/<base>`, or updates the promotion already open with `gh pr edit`; `⌘X` asks `gh repo view` which merge methods the repo allows and whether it deletes merged branches, runs `gh pr merge --squash|--merge|--rebase [--auto]`, and deletes a same-repo head branch on GitHub afterwards through `gh api -X DELETE …/git/refs/heads/<branch>` when asked to (never a fork's, never the local branch or its worktree); `⌘;` opens **Edit pull request** (`pr_actions/edit.rs`) — title, base, draft or ready, labels, reviewers, assignees and its state, read by one GraphQL query as it opens — which sends only what changed, in the order GitHub allows (a reopen first, a deleted base put back at its last commit before it), through `gh pr edit`, `gh pr ready`, `gh pr close` (the branch deleted the same way when ticked) and `gh pr reopen`, and `⌘W` opens that form at its close; `⌘D`, with no form, runs `gh pr ready` on a draft or `gh pr ready --undo` on a ready one. Every call runs off the loop and lands through one channel (`App::pr_actions_tx`). The DIFF VIEWER opened from the modal keeps the modal (`DiffView::back`) and Esc puts it back. A pull request is read from git — `commit_list::read_tip` lists its commits from the merge-base with its base branch, so the COMMIT LIST works on it as on a checkout — its head commit (`headRefOid`) fetched by its pull ref (`refs/pull/N/head`, `conflicts::fetch_pull_head`) when the repo lacks it.

The PR REVIEW (`orion-tui/src/pr_review/`, `⌘⇧R` in the modal) is the modal's review screen, an overlay of its own that keeps the modal to go back to. Its diff is the one the DIFF VIEWER reads for a pull request — `event_loop::read_pr_opening`, then one `git diff` per file from the merge-base to the head, each laid out by `diff_doc` — read on the blocking pool; `layout` sets each review thread under the line it is on (by its `diffSide` and line number) and walks the cursor over lines and threads. The threads come from one GraphQL query (`pr_review::github::read`) asked beside `gh pr view` whenever a page is read, so they ride `PrDetail::threads` into the cache and the page, and again when the screen opens. What it writes (`pr_review::write`) goes into the viewer's pending review through `gh api graphql -X POST --input -`, each request body — the mutation and its variables — on stdin: `addPullRequestReview` with no event starts the pending review when there is none, `addPullRequestReviewThread` adds a comment on a line or a run of lines (`line`/`side`, `startLine`/`startSide`), `addPullRequestReviewThreadReply` a reply, `resolveReviewThread` / `unresolveReviewThread` and `deletePullRequestReviewComment` the rest. One write is in flight at a time, and what it made lands from GitHub's answer rather than a second read. The bar's submit (`pr_review::bar`) is `submitPullRequestReview` on the pending review with the verdict (`COMMENT`, `APPROVE`, `REQUEST_CHANGES` — only `COMMENT` when `viewerDidAuthor`) and the summary, or `addPullRequestReview` with the event when nothing is pending; it then hands back to the modal on the Reviews tab (`pr_modal::land_on`), the page read again. Its answers land through `App::pr_review.tx`, matched to the screen by ticket.

WHAT'S NEW (`orion-tui/src/whats_new.rs`) is a sheet of its own over the grid on the launch after an upgrade, drawn in setup's frame (`onboard::draw_sheet`). Every push to `main` is a release, so `orion-tui/build.rs` bakes each release's notes into the binary from git: the commits between its `v*` tag and the one before, plus the commits since the newest tag under the version the release workflow stamps (which is why the workflow's build job checks out with full history). `seen_version` in config.local.json says which releases are new. Closing the sheet, or setup, stamps it, and it never moves down.

AUTOFIX (`orion-tui/src/autofix.rs`) rides the same lists. Each project's open-PR answer marks the user's own pull requests (`viewerDidAuthor`) that are in trouble as watched, and the git tick asks `gh pr view` for each one's checks, again every minute while some are still running (up to 20 minutes), since check names live only in the body. A settled breakage is fingerprinted (head commit, conflicts, failing check names) against a per-PR ledger kept in the PR cache, so each one is sent once. With **Auto-fix my PRs** on (the default) it is sent at once, unasked: an ordinary `CreatePrAgent` named `autofix-<n>`, on the harness, account, model and effort of the session that worked on the branch, with a `starting_prompt` that holds the PR, what failed — the failing checks under their workflows, and the files `conflicts::local` says its head conflicts in with its base, asked off the loop before the send — wrapped in the **PR autofix** SYSTEM PRESET's text — with no session to copy, it runs on the default agent at that preset's model and effort. A live `autofix-<n>` holds the next send back. Any other session live on the branch is named in the prompt with the path of its Claude transcript (looked up client-side under the account's config dir), and the agent reads it first; if that session already owns the fix it runs `orion autofix stand-down`, a one-shot CLI that renames its own row (`autofix · stood down: <why>`) and archives it through the existing `RenameAgent` / `ArchiveAgent` requests, and the TUI flashes the reason. Nothing in the DAEMON knows about it. SYSTEM PRESETS (`agent_presets::SystemPreset`: PR autofix, Linear Ticket, Week review) are ordinary entries in `agent_presets.json` tagged `"system"`, seeded at startup (adopting a user preset of the same name, and moving any `autofix_*` / `review_*` keys `config.json` still holds into them once), editable but never deleted or renamed. One holding no text says orion's (`SystemPreset::builtin_text`), and the editor saves orion's text back as none.

## How the pieces talk

```
┌──────────── TUI (ratatui) ────────────┐
│  grid: project tabs / bands / rows       │
│  attached terminal: vt100 parser + PTY   │
└───────────────┬───────────────────────┘
                │ unix socket
┌───────────────▼───────────────────────┐
│  Daemon                                 │
│  ┌ registry ┐  ┌ PTY ring buffers ┐   │
│  │ SQLite   │  │ portable-pty     │   │
│  └──────────┘  └──────────────────┘   │
│  ┌ hook HTTP (loopback) ──────────┐   │
│  │ harness hook POSTs             │   │
│  │ → status state machine         │   │
│  └────────────────────────────────┘   │
└───────────────────────────────────────┘
```

**Attach path:** TUI sends `Attach { session, from_seq, cols, rows }`. Daemon replays the PTY ring as `Scrollback`, then streams live `Output`. Keystrokes go the other way as `Input`. Detach does not kill the child.

**Status path (not MCP):** at spawn, Orion writes managed hooks into the worktree (`.claude/settings.local.json` or `.cursor/hooks.json`) or, for Codex, Grok Build and OpenCode, into the CLI's home (`~/.codex/hooks.json`; `~/.grok/hooks/orion.json`, a file of Orion's own that Grok reads with no trust prompt; `~/.config/opencode/plugins/orion.ts`, a plugin that maps OpenCode's events onto the same names). Those hooks `curl` a loopback HTTP server with a per-boot bearer token. Events like `UserPromptSubmit`, `Stop`, `PermissionRequest`, `SubagentStart` feed a status machine that maps to the colored dots (running / finished / needs feedback / …). Stop is gated on active subagents so a turn is not marked done while workers are still going. A launch that hands the CLI a first prompt (a QUICK PROMPT, an AGENT PRESET, a Codex / Cursor / OpenCode PR rule) is created `running` rather than gray: the CLI submits that prompt as it boots, and the row would otherwise sit idle — and sort under every session mid-turn — for the seconds until the first hook lands. Such a row's machine is seeded with a one-shot reprieve for the `9;4;0` the CLI prints as it draws its input box, so the boot is not read as that turn ending. Claude and Codex share one hooks dialect; Cursor speaks its own (camelCase events like `beforeSubmitPrompt`/`stop`, flat `{"command"}` entries, JSON replies on stdout), so its installer translates event names into the `hookEvent` query param and the receiver aliases its payload fields (`conversation_id` → session id, first `workspace_roots` entry → cwd). Cursor has no permission-request hook and runs with `--force`, so cursor agents report busy/idle but never needs-feedback. Grok fires Claude's event names with a camelCase payload (`sessionId` aliased on the shared payload) and has no permission-request hook either, but keeps its own prompts, so a waiting Grok row stays running and the picker row says it can't show waiting (`HarnessDescriptor::status_note`); its AUTO-TITLE instruction rides `--rules` on a fresh launch, since it reads no passive hook's stdout. The `UserPromptSubmit` payload's `prompt` text is captured on the same route — condensed to one line, the newest ten kept per agent row — for the RECENT PROMPTS line each session row carries.

**Auto-title path (hooks again, still not MCP):** a session created with the default `agent-N` name carries a store-only `auto_title_pending` flag. While it's set, the daemon answers the Claude/Codex `UserPromptSubmit` hook POST with an instruction body instead of the usual discarded JSON — the installer's `UserPromptSubmit` command (alone among the hooks) pipes the response to stdout, which those CLIs add to the model's context. The instruction tells the agent to run `orion rename <3-4 word title>` once; that subcommand resolves the agent from `ORION_AGENT_ID`, does a one-shot IPC `AutoRenameAgent`, and the daemon applies it only while the flag is still pending (atomic conditional update), so a user rename — which clears the flag — always wins and repeated attempts get a polite "already titled" error. Claude also gets a `Bash(orion rename:*)` entry merged into `permissions.allow` so the command runs unprompted; Codex/Cursor already run with `--yolo`/`--force`. Cursor's hooks can't inject context, so it gets a managed, env-guarded `.cursor/rules/orion-title.mdc` project rule carrying the same instruction — safe to fire repeatedly because the daemon-side flag is the arbiter. OpenCode's plugin carries it into the turn's system prompt, and Grok Build gets it in `--rules` on a fresh launch.

**Follow-up path:** `Space` on a session row (or **Follow-up prompt** in its menu) opens a small modal over the grid holding the next turn for that agent. `Enter` closes the box and sends `ClientRequest::SendTurn` with the text; the daemon (`Daemon::send_turn`) types it into a live CLI and submits it — the text (a BRACKETED PASTE only when it has line breaks, so a one-liner stays out of the CLI's "[Pasted text]" placeholder), then the carriage return as a write of its own, so the child reads the prompt before the Enter — and boots a dead one (the IDLE REAPER's, or cold since the daemon started) with the text as its first prompt, since a CLI still starting up drops what is typed at it.

**Metrics path:** the footer's memory readout asks the daemon for one reading (`GetMetrics` → `Metrics`) every 5s. The daemon runs a single machine-wide `ps` sweep and sums RSS over each live session's process subtree (the PTY child plus its descendants — an agent CLI fans out into workers and MCP servers), reporting itself separately since sessions are its own descendants. A SPARE WORKTREE's setup and CLI are sessions too, flagged `SessionMetrics.spare` (`SpareBook::sessions`), so the readout counts their memory but not among the agents. The TUI adds its own RSS client-side (it is not a daemon child).

**Remote hosts path:** `orion ssh host [dir]` execs `ssh -t` with a self-installing remote command, and first records the destination in `<data dir>/ssh_hosts.json` (newest first, capped at 20, keyed by host + start dir). The TUI's hosts picker (**SSH hosts** in the command palette, with no key of its own) lists that file; choosing an entry — or typing a new `user@host [dir]` with `a` — quits the TUI cleanly (UI state saved, terminal restored) and hands the destination back to the binary, which execs a fresh `orion ssh` over the same terminal. The local daemon and its sessions keep running; exiting the remote orion lands back in the local shell. `d` in the picker forgets an entry.

**Settings path:** both halves read settings through `orion-core/src/settings.rs`: `config.json` (or `ORION_CONFIG_FILE`) with `<data dir>/config.local.json` merged over it key by key. When the merged object won't deserialize whole, it is read one top-level key at a time, so a value one release can't read costs only that key; the TUI keeps those keys in `Config::skipped`, and a save leaves their stored JSON alone and writes a key the local layer holds back into that layer. Writes go tmp-then-rename through `settings::write_atomic`, which follows a symlink to the file it names, and the presets and hosts lists are read entry by entry, with a save keeping the entries this build can't parse.

**Presets path:** Settings → Presets (`orion-tui/src/presets_tab.rs`) makes, edits and deletes the agent presets in `<data dir>/agent_presets.json` (`orion-tui/src/agent_presets.rs`, a sibling of `ssh_hosts.json`, written tmp-then-rename): each is a name, a harness — FOLLOW THE BOX by default (`AgentPreset::follow_box`: the account and harness of the quick prompt it is picked in, the `⌘N` default with none, through `QuickLaunch::of_preset`), or one it pins — a model / effort choice (or "follow Settings → Accounts") and an optional `text` with `{task}` where the task goes (the end, after a blank line, when it names none). An entry with a `prefix` and a `postfix` reads as prefix, `{task}`, postfix (`agent_presets::migrate_entry`), and the first save — `seed_system`, as orion starts — writes it that way; an entry with no `follow_box` follows when it sits on the default Claude account and keeps any other harness it names, and the next save writes that out. The pickers (`preset_overlays.rs` — the palette's **Agent presets**, `⌘U` / `^X` in the box, `⌘U` over an agent's locked pane, `⇧Tab` on a Linear issue or a todo) only pick: letters type ahead over the names (`fuzzy::rank`, recomputed per key — the list is short — with `AgentPresetsView::selected` kept as the stored index so Enter reads the right row), and `Enter` hands the preset to the box, the pane or a launch. Submitting composes the text with the task at its `{task}` (`AgentPreset::compose`: the marker and the gap round it dropped when the task is empty) and sends `CreateAgent { starting_prompt }`; the daemon validates it (`validate_starting_prompt`: trimmed, never empty, no NUL — its length is the OS's `ARG_MAX` to refuse) and passes it to a cold spawn as the CLI's trailing positional prompt (`claude … "<text>"`, `codex … "<text>"`, `cursor-agent … "<text>"`, `grok … "<text>"`, and `opencode … --prompt "<text>"` — the one CLI whose positional is a project path, so its descriptor's `prompt_flag` carries the text). When the create adopts a SPARE WORKTREE's booted CLI instead, the same text is typed in as its first turn (`send_first_turn`, below). It is request-only — nothing is persisted, so a restart or resume rebuilds the ordinary argv — and the row it creates is an ordinary agent from then on (auto-title, hooks, status, resume).

**Accounts path:** a CLAUDE ACCOUNT is Claude with an account id, never a harness of its own. The registry (`orion-core/src/harness.rs`) builds each `claude_accounts` entry as a copy of Claude's effective row under the account's id, with `CLAUDE_CONFIG_DIR` in its `env` (`claude_account::ClaudeAccount::descriptor`); every descriptor carries the `kind` a session on it is stored as, so a session row is `kind: claude` plus the account's id in `custom_harness` (`HarnessDescriptor::session_kind`, and back through `harness::registry_id` / `harness::resolve`, which refuses a Claude row on an id that is no account). The daemon stores what the resolved row says whatever the request called it, so a create, a sibling, **Continue on** and a resume all land on the right config dir, and model sync, title sync and the transcript checks, which key on Claude, cover every account. Store migration 33 moves any row stored as `custom` + an account id onto `claude`, reading the account ids from the config the daemon loads as it opens the store. What an account has that a harness has — its name, model and effort — lives in one place, its `harnesses.<id>` entry (`claude` for the default account): the Accounts tab, a rename and an add write only there, and `orion-tui/src/config.rs::Config::move_harness_keys` carries a file's flat `claude_model` / `claude_effort` / … keys, an added account's copy of the default account's model and effort, and its `claude_accounts` `name` into those entries once, as the file loads.

**Cursor catalogue path:** `cursor-agent --model` takes one flat id per (family, effort, fast) triple — `claude-opus-5-thinking-high-fast` — and refuses the bracket form its `--help` shows, so the TUI keeps the family as the model and the suffix (`high`, `high-fast`, `fast`) as the effort and the daemon joins them with a `-` at spawn (`registry.rs::agent_spawn_command_with`). `orion-tui/src/cursor_catalogue.rs` builds the lists from one parser over two sources: a built-in seed of the ids observed on 2026-08-28 and `cursor-agent --list-models`, which `bootstrap` (TUI startup, skipped when Cursor is switched off or under `ORION_AGENT_CMD`) reads from `<data dir>/cursor_models.json` and refreshes on a background thread once the cache is a day old; the two are unioned, seed order first, because `--list-models` prints only the featured ids. Most families have no bare id, so "default" effort for them launches the family's fallback (`high`, else `medium`, else its first variant) — `config::fit_effort` is the one place that decides, and every surface that changes the family (Accounts tab, preset editor, picker) runs it.

**Run path:** **Start stack** (`⌘⇧S`, or a row's, a band's or a project tab's right-click menu) sends `StartRun { worktree }` — or `StopRun`, when that worktree's RUN TERMINAL is alive. The daemon reads the project's `run_command` out of `config.json`'s `projects` entry (its own `config.rs`, fresh each time — the TUI's Projects tab writes it) and spawns that line in a terminal row whose `run_command` column is set, as `$SHELL -l -i -c '<prelude>; <run>'` — the agent launch's login-shell wrapper — instead of a bare `-l` shell. One run per worktree: the check-and-spawn holds the spawn gate, a live run is the reply as it stands, and an exited run's row is reused. The PTY's life is the RUNNING state the TUI draws (`TerminalTab.alive` on a row with a `run_command`), and `StopRun` writes a `^C` into it and records the kill's deadline in `stopping_runs`, which every send of the row stamps on as `TerminalTab.run.stopping_until` (so each client counts down to the same moment) until the PTY goes; a second `StopRun`, or `RUN_STOP_GRACE` (two minutes) with it still alive, is `CloseTerminal` on that row. A run terminal is never spawned any other way — `ensure_session` refuses it, the prewarm sweep skips it, the idle reaper spares it — and one whose command exits on its own keeps its `PtySession` and exit code in `finished_runs` (sent as `TerminalTab.run.exit_code`, the run line's `done` / `exited 1`), so an attach replays the output and is sent `SessionExited` straight after. A run whose exit a stop asked for (its id still in `stopping_runs`) is `CloseTerminal`ed instead: the row goes. A run terminal's `PtySession` is spawned with `scan_ports`: `pty::ports::PortScanner` strips escapes off its output and keeps the ports of every `http://localhost|127.0.0.1|0.0.0.0:PORT` it prints, first seen first; a new one fires `PtyEvent::Ports`, on which `watch_for_exit` re-broadcasts the row with `run.ports` read off the live session (so a restart, being a new PTY, starts from none). The TUI draws them after the command as `HitTarget::RunPort` links and ⌘O's **Open app** (`Action::OpenApp`) opens the first. **Restart stack** sends `RestartRun { worktree }`: the daemon checks there is a run command, then stops the run as `StopRun` does with the config kept on its `Stop` entry (`RunState.restarting`); whichever ends the stop — the run's own exit, the second press, or the grace kill — goes through `stop_done`, which starts the run again in the same row (`start_run_with`) instead of `CloseTerminal`. With no run up it is a plain start. ⌘O's **Open command** (`Action::OpenWorktree`, with no key of its own) is TUI-only: it reads the project's `open_command` out of the same `projects` entry and runs it once through `$SHELL -c` in the checkout, detached, output discarded.

**Spare path:** `orion-daemon/src/spare.rs` keeps one SPARE WORKTREE per project used in the last day — in memory only, no rows: a `Spare` holds the checkout (branch and directory `orion-spare-<id>`, `orion_core::SPARE_PREFIX`), the base it was cut from (`git::new_worktree_base`, the ref a cold create would use), its setup PTY (a `TerminalTab` with no row, spawned by `spawn_terminal_session`) and its CLI (an `Agent` with no row, spawned by `spawn_agent_session` on `Config::spare_launch` — the daemon reads `quick_prompt_kind` and `claude_enabled` for it). `git::list_worktrees` drops spare branches, so the sync and `add_project` never adopt one. `tend_spares` runs on `ORION_SPARE_TICK_MS` (30 s) and cuts, reboots, refreshes or removes; a refresh (`refresh_spare`, when `spare_base` — `origin` fetched every 5 min — differs from the spare's) claims the spare in the book's `busy` set, checks it is still on its own branch, `git reset --hard`s it and boots a new CLI, so it can never meet a take, which claims the same way. A `CreateWorktree` carrying `launch` (a `LaunchSpec`: kind, account id, model, effort, mode) goes to `create_launch_worktree`, which `take_spare`s under `worktree_ops` when the spec equals the spare's and the branch is free: `git branch -m`, then under the spare book's lock the worktree row (under the spare's pre-generated id) and a running setup's terminal row — the setup's exit asks `SpareBook::setup_ended` before `command_terminal`, so whichever of the two takes the lock first, the exit lands on the right side — and the CLI parked in `held` for the `CreateAgent`, which `take_held_cli` adopts under the CLI's id and whose `starting_prompt` `send_first_turn` types in once the CLI's `SessionStart` (`SpareBook::note_boot`, from `apply_hook_event`) is in and its ring has stopped growing for 500 ms; a CLI with no `SessionStart` inside a minute is killed and `send_turn` boots it with the task. A held CLI whose create never comes is killed after two minutes or with its worktree (`drop_held_in`). A spare whose setup ends cleanly (or that has no setup command) writes `orion-spare-set-up`, holding the setup command, into its own git admin dir (`<repo>/.git/worktrees/<name>/`, read off its `.git` file); at boot `sweep_spares_at_boot` keeps one spare per project in use whose mark matches the project's setup command now — its CLI booted on the next tick — and removes every other one, any `orion-spare-*` branch no checkout holds, and any `orion-spare-*` directory in the WORKTREE DIR git does not list. `remove_project` removes its spare; a spare's removal releases its containers under **On worktree delete**, as a worktree delete does.

**Setup path:** every checkout the daemon cuts — `create_worktree` (a new branch or an existing one) and `pr_worktree` — ends in `provision_worktree`: its `.env` links, then `start_setup`, which reads the project's `setup_command` from the same `projects` entry and, when there is one, inserts a terminal row with `setup` set (store column `terminals.setup`) and its command in `run_command`, spawned through the same login-shell wrapper by `spawn_command` (shared with `start_run_with`; it sends the row as up only while the PTY is still in `sessions`, so an exit that beat it has the last word). `start_setup` is the one entry point, so anything else that cuts a worktree calls it the same way. Nothing waits on it — the create's Ack goes out at once and the setup runs with no time cap. A setup row is never the worktree's run: `run_terminals_in` filters `setup = 0` and the TUI's `TerminalTab::is_run` excludes it, but everything else a run terminal gets (no respawn from `ensure_session`, the prewarm sweep and the idle reaper leaving it alone) holds for it too. Its exit goes to `setup_ended`: exit 0 is `CloseTerminal`; anything else keeps its PTY and code in `finished_runs`, the TUI's red `setup failed (1)`. A `StartRun` while a setup is alive (`queue_run_behind_setup`, checked under the `queued_runs` lock, which the exit takes only after it has left `sessions`) stores the press's config in `queued_runs` against the setup's id and is answered with that id; every send of the setup row stamps `RunState.run_queued` from it, which the TUI's footer holds as `setup_wait_line`. `setup_ended` takes the entry: a clean exit starts the run with it (`start_run_with`), a failed one warns that the stack didn't start. A `StopRun` while a start is queued only drops the entry (`cancel_queued_run`). `forget_command` clears a terminal's entries in `finished_runs`, `stopping_runs` and `queued_runs` when its row goes or its command starts again.

## Crate layout

| Crate | Role |
|---|---|
| `orion` | Thin CLI: no args → TUI; `add`, `daemon`, `kill`, `rename`, `worktree`, `spawn`, `open`, `config`, `ssh`, `setup`, `app`, `doctor`, `upgrade` (and the hidden `autofix stand-down`) |
| `orion-core` | Shared protocol, entities, IDs, paths, codec |
| `orion-daemon` | PTYs, SQLite, git, hook receiver, status engine |
| `orion-tui` | ratatui UI, keyboard/mouse, attach/scrollback |
| `orion-fuzzy` | The list filters' matcher — dependency-free, and a crate of its own only so dev builds optimise it (`[profile.dev.package.orion-fuzzy]`) |

The TUI also has extras on top of the multiplexer: git diff viewer, grep, the built-in editor (fresh in a modal), fuzzy finders — those are client-side. The daemon is the source of truth for sessions and the tree.

**Input is not action.** In `orion-tui` a key arm and a mouse arm only translate: they say *which row* (`list_hit::row_at` for the pointer) and then call the one function that says *what choosing it does* — `event_loop::activate` for the grid and the modals `event_loop` owns, a modal's own `activate_selected` or `Cmd` executor (`run_settings_cmd`, `file_tabs::run`, `preset_overlays::activate_selected`) for the rest, `select_clicked_row` / `select_*_row` for moving a cursor, `context_menu_items` for the right button's menu. Nothing that closes a modal, sends a request, spawns a process or moves a cursor lives inline in `handle_mouse` or in a key arm beside a twin that does the same. The rule exists because its absence shipped bugs: a click in a pull request's preset picker launched a plain session into the ROOT WORKTREE while Enter launched the PR SESSION, a click in the file finder skipped the markdown reader Enter had learned, and a right-click moved the cursor without the pane. The `INPUT PARITY` tests in `event_loop.rs` build the same app twice, choose a row once by key and once by pointer, and compare everything observable.

**Keys on screen come from the keys.** `orion-tui/src/hints.rs` is the one way a key is put on screen: a registry action's label is spelled from the live keymap (`hints::act`, `KeyChord::display` — a rebind shows everywhere, and an action's ⌘ chord is the one printed), and a modal's own keys live in a small `Key` table (`pr_modal::keys`, `ui::menu_keys`, `launcher::pane_keys`, …) that its key handler matches with `Key::matches` and its hints spell with `Key::hint` — so a hint can never name a key nothing answers. Every modal hangs its hints on its bottom border through `hints::modal_block` (or `hints::draw_on_border` for a modal made of two frames), the FOOTER (`ui/footer.rs`) carries hints only with no modal up, and an explanation names a key as an `{action_id}` token `hints::expand` spells. `hints::assert_hints_from` is the test every modal's hint line passes.

**Every modal moves by one set of keys.** `orion-tui/src/nav.rs` holds them: `Tab`/`⇧Tab` from panel to panel (`nav::PANELS`, `nav::panel`, `nav::cycle` for the order), `←`/`→` sideways inside the panel with the keys (`nav::SIDEWAYS`, `nav::TABS` beside a filter), `↑`/`↓` its rows, `PgUp`/`PgDn`, `Home`/`End`, `Enter` and `Esc` (`nav::CLOSE`, which `hints::ESC_CLOSE` is; every handler's Esc arm asks `nav::closes(&key)`). A modal's key table names one for what it does there — `nav::SIDEWAYS.doing("span")` — and adds a key of its own to a shared one with `Key::also` — `nav::CLOSE.also(&["q"])` — so changing how modals are walked, or closed, is a change to that file. `nav::tests::modals_take_their_moves_from_here` fails on a key table anywhere in the crate that spells `tab`, `shift+tab`, `left`, `right` or `esc` itself, or a handler that asks for a bare `KeyCode::Esc`, unless its `OWN_KEYS` list names the key and says why (a text box's Tab, a form's fields, a wizard's pages).

**A key handler never blocks.** `orion-tui`'s event loop is one task: while a handler runs nothing paints, no PTY output is parsed and no other key is read. So a handler does bookkeeping and nothing else — anything that spawns a process, reads a file of unknown size or waits on the network is a BACKGROUND READ (`view_jobs.rs`: the worktree views' git and disk, keyed by ticket so a late answer nobody is waiting for is dropped) or one of the per-feature channels `main_loop` owns (`gh`, the worktree picker's branch listings), and a view built without a handle — every unit test — reads inline through the same parsers. What the DAEMON will confirm is shown first (`event_loop/optimistic.rs`, `event_loop/placeholder.rs`) and rolled back on Error. `event_loop/pacing.rs` decides when the loop may paint. The INPUT LATENCY PROBE (`perf.rs`, `ORION_PERF_LOG`) and `make perf` are how a change to any of it is judged: handler, paint, settle and echo per scripted step, with peak RSS beside them, because holding more to feel faster is not a trade this codebase makes — the pane's screen cache got quicker by holding less.

**Mental model:** tmux, but the “windows” are agent CLIs bound to git worktrees, and the grid is a mission-control view of which agents are working, waiting, or dead.
